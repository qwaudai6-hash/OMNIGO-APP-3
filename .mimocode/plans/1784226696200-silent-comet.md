# OMNIGO Payment Architecture — Build Plan

## Overview

Build a production-grade payment system for OMNIGO Super App with:
- **Payment Orchestrator** (Go microservice) — central payment routing, idempotency, Saga state, split calculation
- **Postgres Double-Entry Ledger** — source of truth for all money movement (TigerBeetle-ready schema)
- **Escrow System** — vendor funds held 48h after delivery, dispute-gated release
- **COD Cash Flow** — ledger-only entry → rider debt → deep-link settlement → webhook verify
- **Vendor Payout** — hourly batch worker releasing held funds
- **Dispute System** — hold escrow on complaint, resolve before payout

## Architecture Decision

Use **Postgres-based ledger** (not TigerBeetle) for Phase 1. Postgres handles 50K+ transfers/sec which is sufficient until 1M+ orders/day. The schema is designed so migrating to TigerBeetle later is a drop-in replacement.

#### Task 1.1: Database Migration — Ledger Schema
**File:** `infrastructure/postgres/init.sql` (append) + new `infrastructure/postgres/migrations/001_payment_architecture.sql`

Create these tables:

```sql
-- Double-entry ledger entries (every money movement = 2 rows: debit + credit)
CREATE TABLE ledger_entries (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    transaction_id  UUID NOT NULL,          -- groups debit + credit atomically
    account         VARCHAR(50) NOT NULL,    -- admin_revenue, vendor_escrow, rider_wallet, etc.
    amount          DECIMAL(14,2) NOT NULL,  -- positive = credit, negative = debit
    currency        VARCHAR(3) DEFAULT 'PKR',
    reference_type  VARCHAR(30),             -- 'order_payment', 'delivery_credit', 'cod_debt', 'payout'
    reference_id    VARCHAR(50),             -- order_tracking_id or delivery_tracking_id
    description     TEXT,
    idempotency_key VARCHAR(128) UNIQUE,    -- prevent duplicate entries
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_ledger_transaction ON ledger_entries(transaction_id);
CREATE INDEX idx_ledger_account ON ledger_entries(account, created_at);
CREATE INDEX idx_ledger_reference ON ledger_entries(reference_type, reference_id);
CREATE INDEX idx_ledger_idempotency ON ledger_entries(idempotency_key);

-- Escrow holds (vendor funds locked after delivery)
CREATE TABLE escrow_holds (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_tracking_id VARCHAR(50) NOT NULL,
    vendor_tracking_id VARCHAR(50) NOT NULL,
    amount          DECIMAL(14,2) NOT NULL,
    status          VARCHAR(20) DEFAULT 'held',  -- held, released, disputed, refunded
    hold_until      TIMESTAMPTZ NOT NULL,         -- created_at + 48 hours
    released_at     TIMESTAMPTZ,
    dispute_id      UUID,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_escrow_vendor ON escrow_holds(vendor_tracking_id, status);
CREATE INDEX idx_escrow_hold_until ON escrow_holds(hold_until, status);

-- COD debt tracking (rider owes platform after collecting cash)
CREATE TABLE cod_debts (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_tracking_id VARCHAR(50) NOT NULL,
    rider_tracking_id VARCHAR(50) NOT NULL,
    amount_owed     DECIMAL(14,2) NOT NULL,
    status          VARCHAR(20) DEFAULT 'pending',  -- pending, settling, settled, disputed
    settled_via     VARCHAR(30),                     -- jazzcash, easypaisa, bank_transfer
    settled_at      TIMESTAMPTZ,
    webhook_event_id VARCHAR(128),                   -- idempotency on settlement
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_cod_debts_rider ON cod_debts(rider_tracking_id, status);

-- Vendor payouts (settlement records)
CREATE TABLE vendor_payouts (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor_tracking_id VARCHAR(50) NOT NULL,
    amount          DECIMAL(14,2) NOT NULL,
    method          VARCHAR(30),           -- jazzcash, easypaisa, bank_transfer
    status          VARCHAR(20) DEFAULT 'pending',  -- pending, processing, completed, failed
    batch_id        UUID,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    completed_at    TIMESTAMPTZ
);

CREATE INDEX idx_vendor_payouts_vendor ON vendor_payouts(vendor_tracking_id, status);

-- Disputes (hold escrow before release)
CREATE TABLE disputes (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_tracking_id VARCHAR(50) NOT NULL,
    filed_by        VARCHAR(50) NOT NULL,   -- user_tracking_id
    reason          TEXT,
    status          VARCHAR(20) DEFAULT 'open',  -- open, investigating, resolved, rejected
    resolution      TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    resolved_at     TIMESTAMPTZ
);

CREATE INDEX idx_disputes_order ON disputes(order_tracking_id);
CREATE INDEX idx_disputes_status ON disputes(status);
```

### Sprint 2: Online Payment Split + Escrow (Sessions 44-45)

**Goal:** When a customer pays online, the Orchestrator automatically splits: 2% admin, 98% vendor (minus delivery fee), delivery fee to escrow.

#### Task 2.1: Commission Calculator
**File:** `internal/payment_orchestrator/commission.go`

```go
type SplitResult struct {
    AdminRevenue       float64  // 2% of order total
    VendorEscrow       float64  // 98% - delivery_fee
    DeliveryEscrow     float64  // delivery_fee (held for rider payout)
    DeliveryFee        float64  // from delivery gig record
    OrderTotal         float64
}
```

Logic:
1. Read `stores.commission_rate` for this order's vendor (default 2%)
2. Read delivery gig's `delivery_fee` from `deliveries` table
3. Calculate: `AdminRevenue = OrderTotal * CommissionRate / 100`
4. Calculate: `VendorEscrow = OrderTotal - AdminRevenue - DeliveryFee`
5. Calculate: `DeliveryEscrow = DeliveryFee`

#### Task 2.2: Payment Completion Handler (Stripe Webhook → Split)
**File:** `internal/payment_orchestrator/handlers/stripe_handler.go`

When Stripe webhook confirms `payment_intent.succeeded`:
1. Verify signature + idempotency (existing logic)
2. Read order details from DB
3. Calculate split using CommissionCalculator
4. Execute 3 ledger transfers atomically:
   - debit `stripe_holding` (total_amount)
   - credit `admin_revenue` (2%)
   - credit `vendor_locked_escrow` (98% - delivery_fee)
   - credit `central_escrow` (delivery_fee) — will move to rider on delivery
5. Create escrow_hold record (hold_until = NOW + 48h)
6. Emit `payment.split_completed` to Kafka

#### Task 2.3: PayFast Callback → Split
**File:** `internal/payment_orchestrator/handlers/payfast_handler.go`

Same split logic as Stripe, but triggered by PayFast IPN callback.

#### Task 2.4: Escrow Release Worker
**File:** `internal/payment_orchestrator/workers/escrow_releaser.go`

Background goroutine (runs every hour):
1. Query `escrow_holds WHERE status='held' AND hold_until < NOW()`
2. For each hold, check if any open `disputes` exist for this order
3. If no disputes: transfer from `vendor_locked_escrow` → `vendor_withdrawable`
4. Update `escrow_holds.status = 'released'`
5. Emit `escrow.released` event to Kafka

#### Task 2.5: Frontend Integration — No Changes Needed
The existing Stripe Payment Sheet and PayFast redirect flows already work. The Orchestrator hooks into the webhook/callback paths, not the frontend.

### Sprint 3: COD Cash Flow (Sessions 46-47)

**Goal:** Customer pays cash to Rider → ledger-only entry → rider owes platform → deep-link settlement → webhook → ledger update.

#### Task 3.1: COD Confirmation Endpoint
**File:** `internal/payment_orchestrator/handlers/cod_handler.go`

`POST /api/v1/payments/cod/confirm`
- Request: `{ order_tracking_id, rider_tracking_id, amount }`
- Create 2 ledger entries (no real money moved):
  - debit `central_escrow` (amount)
  - credit `rider_cod_debt` (amount) — rider now owes platform
- Create `cod_debts` record with status='pending'
- Update order status to 'cod_pending_settlement'
- Emit `payment.cod_debt_created` to Kafka

#### Task 3.2: COD Pay-Now Deep Link Generator
**File:** `internal/payment_orchestrator/handlers/cod_handler.go`

`POST /api/v1/payments/cod/pay-now`
- Request: `{ cod_debt_id, gateway: "jazzcash"|"easypaisa" }`
- Read cod_debt record, verify status='pending'
- Generate signed deep-link URL:
  ```
  jazzcash://transfer?amount={amount}&to={platform_account}&ref={cod_debt_id}&hash={hmac}
  ```
- Return deep-link to Rider App
- Rider App opens native JazzCash/EasyPaisa (OUTSIDE trust boundary)

#### Task 3.3: COD Settlement Webhook
**File:** `internal/payment_orchestrator/handlers/cod_settlement_handler.go`

`POST /api/v1/payments/cod/settlement`
- Verify HMAC signature + idempotency (webhook_event_id)
- On success:
  - Update `cod_debts.status = 'settled'`
  - Execute 2 ledger transfers:
    - debit `rider_cod_debt` (clear debt)
    - credit `admin_revenue` (1-1.5%)
    - credit `vendor_locked_escrow` (98.5-99%)
  - Create escrow_hold for the vendor portion
  - Emit `payment.cod_settled` to Kafka

#### Task 3.4: Rider App — COD Debt Display
**File:** `frontend/omnigo_app/lib/features/rider/presentation/screens/rider_wallet_screen.dart`

- Add "COD Debt" section showing `rider_cod_debt` balance
- Show "Pay Now" button that calls `/api/v1/payments/cod/pay-now`
- Open deep-link via `url_launcher`

#### Task 3.5: Flutter Deep-Link Handler
**File:** `frontend/omnigo_app/lib/features/rider/services/deep_link_handler.dart`

- Handle `jazzcash://` and `easypaisa://` deep-links
- Open native app via `url_launcher`
- Return to OMNIGO app after payment

### Sprint 4: Vendor Payout + Dispute System (Sessions 48-49)

**Goal:** Automatic vendor settlement and dispute-gated escrow holds.

#### Task 4.1: Vendor Wallet Table
**File:** `infrastructure/postgres/migrations/002_vendor_wallet.sql`

```sql
CREATE TABLE vendor_wallet (
    id                  BIGSERIAL PRIMARY KEY,
    vendor_tracking_id  VARCHAR(50) UNIQUE NOT NULL,
    balance             DECIMAL(14,2) NOT NULL DEFAULT 0 CHECK (balance >= 0),
    lifetime_earnings   DECIMAL(14,2) NOT NULL DEFAULT 0 CHECK (lifetime_earnings >= 0),
    total_payouts       DECIMAL(14,2) NOT NULL DEFAULT 0,
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

#### Task 4.2: Payout Releaser Worker
**File:** `internal/payment_orchestrator/workers/payout_worker.go`

Background goroutine (runs every hour):
1. Query `escrow_holds WHERE status='released'`
2. Group by `vendor_tracking_id`
3. For each vendor:
   - Check for open disputes on any of their orders
   - If no disputes: sum released amounts → create `vendor_payouts` record
   - Execute ledger transfer: debit `vendor_withdrawable` → credit vendor's external account
   - Emit `payout.completed` to Kafka
   - Update vendor_wallet.total_payouts

#### Task 4.3: Dispute Filing Endpoint
**File:** `internal/payment_orchestrator/handlers/dispute_handler.go`

`POST /api/v1/payments/disputes`
- Request: `{ order_tracking_id, reason, photo_url }`
- Create `disputes` record with status='open'
- Update related `escrow_holds.status = 'disputed'`
- Emit `dispute.filed` to Kafka

#### Task 4.4: Dispute Resolution Endpoint
**File:** `internal/payment_orchestrator/handlers/dispute_handler.go`

`PATCH /api/v1/payments/disputes/:id`
- Request: `{ status: "resolved"|"rejected", resolution }`
- If resolved: refund to customer via Stripe reversal
- If rejected: release escrow normally
- Update `disputes` record

## Risk Mitigations

| Risk | Mitigation |
|------|-----------|
| Ledger inconsistency | Atomic Postgres transactions for every transfer pair |
| Double-spending | Idempotency keys on every ledger entry (UNIQUE constraint) |
| Webhook spoofing | HMAC-SHA256 + timestamp + idempotency verification |
| Race conditions | SELECT FOR UPDATE on order status, serialized escrow release |
| Service crash mid-transfer | Ledger entries are atomic (both debit+credit in same tx) |
| COD rider fraud | Ledger-only entry, no trust on rider — settlement via signed webhook only |

## Execution Order

1. **Sprint 1** (Sessions 42-43): Ledger schema + Orchestrator scaffold + transfer engine
2. **Sprint 2** (Sessions 44-45): Online payment split + escrow hold/release
3. **Sprint 3** (Sessions 46-47): COD cash flow + deep-link + settlement webhook
4. **Sprint 4** (Sessions 48-49): Vendor payout worker + dispute system
5. **Sprint 5** (Sessions 50-51): Integration tests + fail-closed idempotency + Docker + monitoring
